- [x] 定義 acceptance 證據與最小持久狀態的責任分工，為正常完成、缺證據、需求未變但受驗內容或驗證條件已改、session 恢復、寫入中斷、回應遺失及並行變更列出權威、commit point、重試與停止條件，且完成證據能追溯到成果契約、受驗內容及相關驗證條件
- [x] 在專案外完成可重現的最小候選原型與收集設定：執行邊界檢查並記錄期望／實際結果，以可控 trace 檢查額外請示、修正與錯誤完成的辨識，確認雙 host 載入指定套件，最後凍結候選、workflow prompts、adapter／scorer 雜湊；列明程式強制與 Agent 責任，正式套件及真實 proposal 不受修改

- [x] 將設計與實測結果整理到本提案結論，提出有依據的採用、修正或否決建議，列出後續最小實作範圍、runtime 責任、舊 proposal 相容性／遷移與失敗恢復策略，以及尚待決策事項；驗證每項成效主張皆有觀察或實驗依據，且未把候選流程直接發布

## 驗收條件
以下候選行為情境是必須檢查並記錄實際結果的研究問題，也是建議採用的必要條件；候選失敗須判為未達標，但不阻止已完成約定檢查及有效 pilot 的研究以否決結論結案。缺少觀察或未完成量測不等於候選的有效失敗。

- 情境：讀取研究結果，能指出哪些成果、acceptance、限制與風險屬於核准契約，哪些施工步驟可由 Agent 自行調整；三類案例均有完整流程及停止條件。
- 情境：成果契約不變，只調整修改順序、拆合內部步驟或搜尋方法，候選流程可繼續，無需因舊 task 文字或順序不同而重新核准；若調整改變授權成果、範圍或重要風險，則必須停止並重新核准。
- 情境：checkpoint 涵蓋多個相依檔案修改時，仍有清楚的可驗證成果與 acceptance 對應；必要驗證失敗、缺少證據，或需求未變但受驗內容／必要驗證條件已改時，不能直接沿用舊成功結果或用完成報告取代驗證。
- 情境：沒有專案宣告的品質指令，流程仍能提出適用的 acceptance 證據；不憑空新增全專案 lint、coverage 或其他品質門檻。
- 情境：session 中斷、回應遺失或狀態被並行修改，設計能說明可信來源、已提交與未提交的區分、恢復與重試條件，不覆蓋較新授權、不重複不可逆副作用、不以時間戳猜測權威。
- 情境：原型有可重新執行的邊界檢查及期望／實際結果，明列 Agent 承諾和 runtime 強制能力；未核准修改、未重核准擴張範圍及無證據完成均不能被算成候選成功，真實失敗保留並可支持否決結論。
- 情境：pilot 有 6 組配對、12 次有效 run，兩邊需求、fixtures、驗收與 host／model 條件可核對；收集前已有候選、workflow prompts、adapter／scorer 的凍結雜湊及雙 host 載入證據，真實失敗保留、環境無效另列，實驗輸入改動不混算，且新流程不因沒重演舊 CLI 順序或使用不同產物路徑而被誤判。
- 情境：比較結果包含驗收成功、越界與錯誤完成、返工、人工介入、turns、tool calls、tokens、牆鐘時間及小樣本限制；腳本預定 turns 與核准次數不充當人工介入改善的證據，額外請示與修正循環有 trace 定位，未知不記零，事後 oracle 通過不抹除當時缺少證據的完成宣告；未達事前門檻或發生安全違規時如實否決／修正，不以縮短 SKILL 或較低 tokens 抵銷失敗。
- 情境：最終結論足以決定是否另立正式改版提案，並指出舊 proposal 如何讀取、核准與完成證據是否仍有效、是否需要遷移及如何恢復；不把研究設計假設寫成已實現的產品能力。
- 情境：本研究維持 `simplify-skill-release-evals`、既有未提交產品修改、已安裝 Skill、歷史 eval evidence 與發版政策不變；研究結論初始為空，僅在核准後填入實際觀察。
