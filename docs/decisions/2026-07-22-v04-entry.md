# Defer the v0.4 transaction engine

Historical decision: superseded later on 2026-07-22 by `docs/decisions/2026-07-22-v04-entry-reassessment.md` after the completed dogfood corpus was quantified as new usage evidence.

## Date
2026-07-22

## Versions
- Engine: `0.3.0`
- Skill: `v0.3.0` candidate based on commit `5facfaca4c1e339d69fb2c14ac26c33062c5596f`
- Environment: post-adoption macOS/Linux test matrix and fresh Codex/Claude Code sessions

## Question and gate
Does repository evidence justify starting `add-machine-metadata-and-approval-manifest`, the first v0.4 transaction-engine proposal?

The roadmap requires at least one repeated, persisted case involving stale mutation context, wrong task identity, managed-state drift, archive/INDEX partial transition, multi-user friction, or enough real usage that deterministic mutation clearly reduces manual verification cost. Successful v0.3 CLI adoption is necessary but not sufficient.

## Evaluated scenarios
- Review every recorded entry in `docs/friction-log.md` against the v0.4 entry criteria.
- Review the readonly adoption decision for repeated bypass, completion-rate regression, or evidence that status/checkbox/archive mutation is currently unsafe.
- Distinguish evidence produced by real workflow operation from concerns described only in the roadmap design.

## Observed evidence
- `F-20260722-01` concerns an unreachable public-CLI pilot scenario, not mutation correctness.
- `F-20260722-02` concerns agent permission classification for CLI execution; it was mitigated by the standard `python3 .../sdd.py` invocation and does not support adding mutation calls.
- `F-20260722-03` concerns pyenv stderr noise in a read-only sandbox, not stale writes or managed-state drift.
- Fresh-session evidence in `docs/decisions/2026-07-22-readonly-parsing-adoption.md` shows both tools can follow one readonly CLI call and fail closed. It contains no repeated real proposal mutation failure.
- The repository has no recorded archive/INDEX partial transition, wrong-task completion, out-of-band status/checkbox drift, or multi-user collision.

## Rejected alternatives
- Start v0.4 because its proposals already exist: rejected because roadmap completeness is explicitly not entry evidence.
- Treat hypothetical failure-injection cases as real friction: rejected because those tests validate an implementation after entry; they do not justify the investment.
- Use successful readonly adoption alone as sufficient evidence: rejected because mutation adds metadata and extra command calls whose cost must be justified independently.

## Decision
`DEFER`. Keep v0.3 as the stable script-read/prose-write plateau. Do not approve or implement `add-machine-metadata-and-approval-manifest` until a new entry decision cites persisted qualifying evidence.

## Rollback boundary
No v0.4 artifact, metadata, or command is activated, so no rollback or migration is required. If v0.3 readonly adoption later regresses, use the separate v0.3 rollback boundary and pin prose-only `v0.2.4`.

## Follow-up
- Record real mutation or collaboration friction in `docs/friction-log.md` as it occurs, without inventing incidents or storing sensitive transcripts.
- Re-evaluate this gate when at least one qualifying problem repeats or usage evidence shows a clear manual-verification cost.
- If the gate changes to `GO`, explicitly approve the still-draft `add-machine-metadata-and-approval-manifest` proposal before implementation.
